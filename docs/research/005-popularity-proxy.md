# Open-data sources for the Popularity Proxy

Ticket: [wayfinder/tickets/005-research-popularity-proxy.md](../../wayfinder/tickets/005-research-popularity-proxy.md). Vocabulary per [CONTEXT.md](../../CONTEXT.md): an **Album** is a MusicBrainz release group, an **Edition** a MusicBrainz release; the **Popularity Proxy** stands in for the **Community Score** while an Album has too few native Ratings. The blend formula is ticket 010's decision; this note only establishes what each source offers, on what terms, and how it keys to Albums.

Every live-API observation below was made on 2026-09-02 from a plain HTTP client with an identifying `User-Agent`, no account, no key, no payment. Numbers quoted from live endpoints are point-in-time samples, not guarantees.

## Answer in brief

**Widest coverage at lowest legal risk: ListenBrainz release-group popularity (listen and listener counts, CC0 data, MBID-keyed) as the primary Popularity Proxy, MusicBrainz native ratings (CC BY-NC-SA 3.0, MBID-keyed) as the secondary, and Wikipedia pageviews (CC0, keyed through Wikidata's MusicBrainz release group ID) as an attention signal for the ~150k Albums that have an English Wikipedia article.** All three key on the Album's own MBID with no name matching, need no account, and permit storing and displaying the numbers. Everything else is either licensed for non-commercial/private use only with no storage allowance (Last.fm, Deezer), contractually forbidden from being stored or blended with other services' data (Spotify), or subject to a six-hour display-freshness rule that makes a stored proxy impossible (Discogs).

**Quality signals in open data are thin but real:** Wikidata carries structured review scores (`P444` + `P447`) on ~4,100 Albums and award wins/nominations (`P166`/`P1411`) on ~2,300, all CC0. Year-end list placements are *not* structured anywhere open; they live as prose in Wikipedia "Accolades" sections (CC BY-SA 4.0) and as the `{{Album ratings}}` template in article wikitext, which is a cited, per-Publication score table that could seed ticket 004/008's Critic Review sourcing rather than the Popularity Proxy.

## Per-source findings

### ListenBrainz

**Endpoints.** The popularity API "return[s] the total listen and listeners count for various entities and also a way to query top entities for a given artist" ([popularity.html](https://listenbrainz.readthedocs.io/en/latest/users/api/popularity.html)). `POST /1/popularity/release-group` takes `release_group_mbids` and returns, in input order, `release_group_mbid`, `total_listen_count`, `total_user_count`, with nulls where no stats exist; batch size is `MAX_ITEMS_PER_GET`, defined as 1000 in the core constants ([core.html](https://listenbrainz.readthedocs.io/en/latest/users/api/core.html)). The docs list no auth requirement for the POST endpoints.

**Observed.** Unauthenticated POST on 2026-09-02 returned HTTP 200:

```
OK Computer   b1392450-e666-3926-a536-22c65f834433  listens 1,552,350  listeners 21,564
Nevermind     1b022e01-4da6-387b-8658-8678046e4cef  listens 1,311,799  listeners 25,010
(nil MBID)    00000000-0000-0000-0000-000000000000  null / null
```

Response headers: `X-RateLimit-Limit: 30`, `X-RateLimit-Remaining: 29`, `X-RateLimit-Reset-In: 6`. The two `GET /1/popularity/top-*-for-artist/{mbid}` endpoints now refuse anonymous calls with HTTP 401: `"Due to bad actors and AI scrapers causing undue traffic on our sites, you need to provide an Auth token for this endpoint."` The source confirms the GETs call `ensure_user_token_for_expensive_endpoint()` while the POSTs carry only `@crossdomain` and `@ratelimit()` ([popularity_api.py](https://raw.githubusercontent.com/metabrainz/listenbrainz-server/master/listenbrainz/webserver/views/popularity_api.py)). A free LB account would lift this, but the POST path is the one we need and it is open.

**Sitewide statistics** (`/1/stats/sitewide/release-groups?range=all_time`) return `release_group_mbid` + `listen_count` but are capped to a top-N list per range (docs: "calculate the top 1000") and are batch-recomputed: the all-time payload observed `last_updated` 1785148578 (2026-07-27) and `to_ts` 2026-07-27, while `listening-activity` was `last_updated` 1787637216 (2026-08-25) ([statistics.html](https://listenbrainz.readthedocs.io/en/latest/users/api/statistics.html)). The sitewide figure for OK Computer (1,254,408) differs from the popularity endpoint's (1,552,350), so the two are computed differently and must not be mixed. Summing the all-time `listening-activity` buckets gives 2,519,867,367 listens (2002–2026).

**Rate limiting.** "If the client exceeds the number of requests allowed, the server will respond with error code `429: Too Many Requests`"; "Requests that provide the _Authorization_ header with a valid user token may receive higher rate limits than those without valid user tokens" ([api/index.html](https://listenbrainz.readthedocs.io/en/latest/users/api/index.html)). Headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset-In` (recommended), `X-RateLimit-Reset`.

**Licence.** MetaBrainz lists "ListenBrainz PostgreSQL Data Dumps" under "Creative Commons Zero (CC0)", commercial use allowed, "financial support ... strongly urged, even for CC0 data" ([metabrainz.org/datasets/postgres-dumps](https://metabrainz.org/datasets/postgres-dumps)). Full dumps "twice a month, on the 1st and 15th, with incremental dumps daily" (same page; also [listenbrainz-dumps.html](https://listenbrainz.readthedocs.io/en/latest/users/listenbrainz-dumps.html)). The API responses themselves state no licence; the popularity dataset is described only as one that "analyses listens" ([ListenBrainz 2023 recap](https://blog.metabrainz.org/2024/02/26/listenbrainz-2023-recap/)). See the unverified list: the dataset-hoster page for a *related* dataset says it derives from MLHD+, which MetaBrainz labels non-commercial.

**Keys.** Native release group MBIDs. Nothing to match.

### MusicBrainz native ratings

**What.** "The rating system allows users to rate MusicBrainz entities (artists, labels, release groups, recordings, events, works)"; users "assign a value between 1 and 5"; "these values are then aggregated by the server to compute an average community rating" ([Rating_System](https://musicbrainz.org/doc/Rating_System)). API: "All entities except area, place, release, and series support: ratings, user-ratings" as `inc=` arguments ([MusicBrainz_API](https://musicbrainz.org/doc/MusicBrainz_API)). Observed for OK Computer with `inc=ratings+tags&fmt=json`: `"rating": {"value": 4.55, "votes-count": 88}`; tags `alternative rock` (25), `art rock` (13), `rock` (13).

**Coverage.** Statistics page (last updated 2026-09-02): release groups 4,493,395; "Ratings (raw / aggregated)" 1,739,459 / 1,305,018 across all six rateable entity types; tags raw 20,304,022 / aggregated 243,786 ([musicbrainz.org/statistics](https://musicbrainz.org/statistics)). The page does not break ratings out by entity type.

**Rated release groups.** Computed from mbdump-derived 2026-08-29 (ticket 002 research): release groups with a MusicBrainz rating = **253,421 of 4,486,409 (5.6%)**; of those, 212,726 have exactly one vote, 35,083 have 2–4 votes, and only **5,612 have 5+ votes**. So a vote-count floor of 5 leaves roughly 0.1% of Albums with a usable MusicBrainz rating; as a Popularity Proxy input it is a thin secondary, not a backbone.

**Licence.** "The derived data consists of annotations, user ratings, user tags, and search indexes"; `mbdump-derived.tar.bz2` is listed under CC BY-NC-SA 3.0, while `mbdump.tar.bz2` (core) is CC0 ([MusicBrainz_Database/Download](https://musicbrainz.org/doc/MusicBrainz_Database/Download); [About/Data_License](https://musicbrainz.org/doc/About/Data_License): "The core data of the database is licensed under the CC0 ... The remaining portions of the database are released under the Creative Commons Attribution-NonCommercial-ShareAlike 3.0 license"). So ratings and tag counts, whether read from the dump or the API, are BY-NC-SA: attribute MusicBrainz, no commercial use, and any Popularity Proxy value derived from them is share-alike. MetaBrainz's dumps page adds that commercial use of core data is permitted but support is "strongly urged".

**Freshness.** Live API; full dumps "Twice a week, Wednesdays and Saturdays" ([postgres-dumps](https://metabrainz.org/datasets/postgres-dumps)).

**Rate limit.** Per IP: "Currently that rate is (on average) 1 request per second"; global "We allow through 300 requests each second (on average), and decline (http 503) the rest"; anonymous or generic user-agents are throttled, format `Application name/<version> ( contact-url )` ([Rate_Limiting](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)). At 1 req/s, refreshing 4.5 M Albums via the API is impossible; the dump is the path.

**Keys.** Native.

### Wikipedia pageviews and Wikidata

**Keying.** Wikidata property `P436` "MusicBrainz release group ID" ([Property:P436](https://www.wikidata.org/wiki/Property:P436)). SPARQL counts on 2026-09-02: 243,920 items carry `P436`; 148,523 of those have an English Wikipedia sitelink; 133,022 also carry a Discogs master ID (`P1954`); 30,207 a Spotify album ID (`P2205`). MusicBrainz links back: the OK Computer release group's `url-rels` include `wikidata → https://www.wikidata.org/wiki/Q202996` and `discogs → https://www.discogs.com/master/21491` ([release-group lookup](https://musicbrainz.org/ws/2/release-group/b1392450-e666-3926-a536-22c65f834433?inc=url-rels&fmt=json)). Wikidata: "All structured data in the main, property and lexeme namespaces is made available under the Creative Commons CC0 License" ([Wikidata:Licensing](https://www.wikidata.org/wiki/Wikidata:Licensing)).

**Pageviews.** Per-article endpoint `/metrics/pageviews/per-article/{project}/{access}/{agent}/{article}/{granularity}/{start}/{end}`; "These endpoints serve data starting on July 1, 2015" ([page-views reference](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html)). Observed `en.wikipedia/all-access/all-agents/OK_Computer/monthly/2025010100/2025123100`: 40,515 (Feb) to 62,378 (Sep) views per month. Access policy: "Data provided by the API is available under the CC0 1.0 license"; "The API requires an HTTP User-Agent header for all requests"; clients without one "may be blocked without notice"; "Rate limits are dependent on the client's identity and level of access" ([access-policy](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/documentation/access-policy.html)). The REST spec's global rule: "Limit your clients to no more than 200 requests/s to this API" and "Set a unique `User-Agent` or `Api-User-Agent` header" ([wikimedia.org/api/rest_v1/?spec](https://wikimedia.org/api/rest_v1/?spec)). Wikimedia's cross-platform policy is stricter and per-minute: 10/min unidentified, 200/min for User-Agent-only bots, applying to "the Action API and REST APIs" ([Wikimedia_APIs/Rate_limits](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits)). Plan for 200/min: a monthly refresh of ~150k Albums is ~12.5 hours of polite polling.

**Quality signals in Wikidata.** `P444` "review score received by a creative work or other entity", qualified by `P447` "issuer of a review score" and `P7887` number of reviews ([P444](https://www.wikidata.org/wiki/Property:P444), [P447](https://www.wikidata.org/wiki/Property:P447)); `P1411` "award nomination received by a person, organisation or creative work" with `P585` point in time ([P1411](https://www.wikidata.org/wiki/Property:P1411)); `P166` award received. Counts restricted to items with `P436`: review scores 4,056; award or nomination 2,337; `P1352` ranking 4 (so year-end list placements are effectively absent). External-ID properties exist for Acclaimed Music (`P12075`, 4,087), Album of the Year (`P7067`, 8,946), Metacritic (`P1712`, 11,961) and Rate Your Music release (`P8392`, 8,101) but they are links, not scores; using them would mean scraping sites the map rules out.

**Quality signals in Wikipedia.** Album articles carry a `{{Album ratings}}` template: "This template provides a brief summary and overview of the critical consensus of song and album reviews", with `rev1`/`rev1score` ... and `MC` (Metacritic), `aggregate1`; "Only add a rating if you cite it with a reference" ([Template:Album_ratings](https://en.wikipedia.org/wiki/Template:Album_ratings)). OK Computer's wikitext lists ten cited contemporaneous scores (Chicago Tribune 3.5/4, Guardian 4/5, NME 10/10, Pitchfork 10/10, Q 5/5, Rolling Stone 4/5, Spin 8/10 ...) and an "Accolades" section naming year-end placements in prose ([action=raw](https://en.wikipedia.org/w/index.php?title=OK_Computer&action=raw)); the parsed article has a top-level "Critical reception" section ([action=parse](https://en.wikipedia.org/w/api.php?action=parse&page=OK_Computer&prop=sections&format=json)). Text is CC BY-SA 4.0 and GFDL; reuse requires credit "Through hyperlink (where possible) or URL to the article" ([Wikimedia Terms of Use](https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use)). Action API etiquette: serial requests, descriptive User-Agent, `maxlag` for non-interactive jobs ([API:Etiquette](https://www.mediawiki.org/wiki/API:Etiquette)). The standing decision is that Critic Score is aggregated from Publications directly, so this template is a *finding aid* for tickets 004/008 (which Publications reviewed which Albums, with citations), not a Signal in itself.

### Discogs

**API.** `GET /releases/{id}` returns `community.have`, `community.want`, `community.rating.{average,count}` (docs example `"have": 252, "want": 42`); `GET /releases/{id}/rating` returns average and count; `GET /masters/{id}` has no `community` block; `GET /masters/{id}/versions` lists releases with `stats.community.in_wantlist` / `in_collection` ([developers](https://www.discogs.com/developers)). Search "Authentication (as any user) is required" and accepts `barcode`, `catno`, `type=master` (same page). Observed unauthenticated: master 21491 (OK Computer) → `main_release` 4950798 → `have 11669, want 18229, rating 4.71 (1280)`; versions listing: 248 releases, each with `in_collection`/`in_wantlist`. **The documented `GET /releases/{id}/stats` (`num_have`/`num_want`) returned `{"is_offensive": false}` for both the docs' example (249504) and a live release**, so treat it as gone.

**Rate limit.** "Authenticated requests are limited to 60 per minute, and unauthenticated requests are limited to 25 per minute ... moving average over a 60 second window"; a unique User-Agent is required or the app is "silently block[ed]" ([developers](https://www.discogs.com/developers)). Observed headers `x-discogs-ratelimit: 25`.

**Terms** (Last Updated May 27th, 2025, [API Terms of Use](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use)). CC0 Data: "Release titles, notes, dates, format, track listings, barcodes and other identifiers, credits, versions, URL links ...; Artist names ...; Label ... names". Restricted Data: "'Discogs User Data' - Required category: username; ... Optional categories ...: ... collection, and wantlist", "Marketplace Data", "Images". Aggregate have/want counts are named in neither list. Storage: "The Content within Our API is dynamic and is quickly outdated. You may not display in any format or to any audience the Content if it is more than six (6) hours older than the information on Our online properties or applications and applications. You may not cache or store the Content longer than is necessary to provide a service to Your application's users." Attribution: "you must display the following notice directly next to any data You use from the Discogs API: 'Data provided by Discogs.' The notice must include a hyperlink to the discogs.com page that includes the data. The link back must not use any mechanism that prevents passing along search engine ranking credit to that page, such as 'nofollow'", plus a prominent "This application uses Discogs' API but is not affiliated with, sponsored or endorsed by Discogs" notice. Commercial use "generally permitted" except listed cases; Restricted Data may not be used "for any commercial purposes" or transferred. Monthly dumps of "Release, Artist, Label, and Master Release data" are CC0 ([data.discogs.com](https://data.discogs.com/)).

**Assessment.** Have/want is Edition-level (sum ~250 versions per popular Album), the six-hour display rule forbids a stored proxy, and at 60 req/min (86,400/day) a six-hourly refresh covers ~21,600 Editions — a rounding error against the Catalog. Discogs stays what the map already says: an acceptable secondary *Catalog* source via the CC0 dump, not a Popularity Proxy input.

An API key is required; "Please use an identifiable User-Agent header on all requests"; "Your account may be suspended if your application is continuously making several calls per second or if you're making excessive calls" ([api/intro](https://www.last.fm/api/intro)).

All links to Last.fm from pages displaying information on an artist, album or track should link to the appropriate catalogue page on Last.fm. ... All button/link placements are subject to approval by Last.fm and Last.fm can suggest the use of a button/link of its choice for You to use if Last.fm deems necessary. - 4.2.1–4.2.2: the licence is conditional on "Making reference to the licence granted by Last.fm ... on all copies of the Last.fm Data, Derivative Works and/or Collective Works published" and "Crediting Last.fm in the form set out in Clause 2.7 where You have used Last.fm Data or created a Derivative Work and/or Collective Work that You publish".

Two integers per Album would fit millions of Albums inside 100 MB, but the written-approval and non-commercial clauses put a public AGPL site at Last.fm's discretion. Coverage and MBID-lookup reliability could not be tested without a key. Low priority; revisit only if Sam wants to email partners@last.fm.

### Deezer

**API.** Public, keyless: `GET https://api.deezer.com/album/302127` returned Daft Punk *Discovery* with `fans: 340306`, `upc: "724384960650"`, `nb_tracks`, `release_date`, `label`, `genre_id`; `GET /album/upc:724384960650` resolves the same album by UPC, and an unknown UPC returns `{"error": {"type": "DataException", "message": "no data", "code": 800}}`. `search/album?q=...` returns `nb_tracks` but no fans/rank on results. That UPC also resolves in MusicBrainz: `release?query=barcode:724384960650` → two Editions in release group `48117b90-a16e-34ca-a514-19c702df1158` ([MB search](https://musicbrainz.org/ws/2/release?query=barcode:724384960650&fmt=json)).

**Docs.** [developers.deezer.com/api](https://developers.deezer.com/api) and `/api/album` render only "You have to login to accept the terms and conditions of the simple API", so the album object reference and any rate limit are not publicly citable.

**Terms** ([termsofuse](https://developers.deezer.com/termsofuse)), verbatim: "The Developer agrees that the use of the Services is strictly limited for a non-commercial purpose and in a non-commercial environment. It means that the Developer shall not perceive, receive, generate, benefit or create directly or indirectly, any moneys, incomes, revenues, data or any other consideration in connection with the use of neither the Services themselves, nor any and all Content accessed through the Services." Also: "The use of the Content is limited to a strictly private use within a family scope"; trademark use governed by login-gated "Trademark Guidelines"; French law. No storage or caching clause at all.

**Assessment.** Terms are written for personal widgets ("Personal Applications"), forbid generating even "data" as consideration, and confine Content to family-scope private use. A public multi-user site is outside them. Exclude.

### Spotify (cross-check for ticket 003)

`popularity`: "The popularity of the album. The value will be between 0 and 100, with 100 being the most popular"; `external_ids` carries `upc`, `ean`, `isrc` ([get-an-album](https://developer.spotify.com/documentation/web-api/reference/get-an-album)). Developer Terms, "Storing Spotify Content": "Except as otherwise set out in these Developer Terms, you may not store, aggregate or create compilations or databases of Spotify Content, other than as strictly necessary to operate your SDA. You must use reasonable efforts to ensure that any data you display to users is the most up to date data available through the Spotify Platform, and to delete older data. Do not store Spotify Content indefinitely." "Local caching. Do not locally cache any Spotify Content, except as strictly necessary to enhance the performance of your SDA and its functionality, and limited to the temporary caching of: metadata and cover art; or Conditional Downloads of sound recordings" ([developer.spotify.com/terms](https://developer.spotify.com/terms)). Developer Policy III.5: "Do not create any product or service which is integrated with streams or content from another service"; III.14: no ML/AI training on Spotify Content; II.4.1: "If you display any Spotify Content you must clearly attribute the content as being supplied and made available by Spotify, by using the Spotify Marks"; II.4.3: "You must not offer metadata, cover art, and/or Audio Preview Clips as a standalone service or product" ([developer.spotify.com/policy](https://developer.spotify.com/policy)). A Popularity Proxy is by definition a stored, aggregated, blended database of other services' content, so Spotify's `popularity` is out. Spotify remains an Import Source only (standing decision); ticket 003 owns the Import-side terms.

## Recommended combination

1. **ListenBrainz `POST /1/popularity/release-group`** — primary. Native MBIDs, 1000 per call, no account, nulls for unknowns, CC0 dumps. Refresh the whole Catalog in ~4,500 calls (at the observed 30-per-window limit, well under a day), or read it from the twice-monthly dump. Store `total_listen_count` and `total_user_count`; listener count is the more robust of the two.
2. **MusicBrainz ratings** — secondary, from `mbdump-derived` (`release_group_meta.rating`, `rating_count`). Only Albums with `votes-count` above a floor (010's call) should count. Accepting this data makes the derived proxy CC BY-NC-SA; this needs a yes/no from Sam because it is the only non-CC0 input in the recommended set.
3. **Wikipedia monthly pageviews** — tertiary, attention rather than listening, ~150k Albums, CC0, keyed through Wikidata `P436` (or MB's `wikidata` URL relationship). Cheap to refresh monthly.
4. **Wikidata `P444`/`P166`/`P1411`** — quality flags on a few thousand Albums, CC0. Useful as a Reason ("Mercury Prize nominee") more than as a number.

Excluded: Spotify (storage and blending forbidden), Deezer (non-commercial, private-use terms, gated docs), Last.fm (non-commercial, page approval, 100 MB cap), Discogs (six-hour display rule, Edition-level only, have/want licence status unstated).

Attribution the site must carry for the recommended set: MusicBrainz (BY-NC-SA) on any page showing a value derived from ratings; nothing required for ListenBrainz, Wikidata, or pageviews, though a "data from MetaBrainz / Wikimedia" line is good manners and MetaBrainz asks for support.

## Not verified

- **ListenBrainz popularity provenance and licence.** The API docs and source do not say what the popularity counts are computed from. The dataset hoster's *popular-releases-by-listeners* page says it derives from the "Music Listening History Dataset Plus" ([datasets.listenbrainz.org](https://datasets.listenbrainz.org/popular-releases-by-listeners)), which MetaBrainz lists with "Commercial use: Not allowed, as per original dataset terms" ([derived-dumps](https://metabrainz.org/datasets/derived-dumps)). Whether the `/1/popularity/*` numbers include MLHD+ or only CC0 LB listens is not documented. Ask on the MetaBrainz forum or IRC before relying on the API numbers commercially; the CC0 listens dump sidesteps the question entirely.
- **ListenBrainz rate-limit window size.** Observed `X-RateLimit-Limit: 30` with `Reset-In: 6`; the window length is not documented.
- **MusicBrainz ratings by entity type.** The statistics page gives only the all-entity total; the release-group figures above come from ticket 002's count of the 2026-08-29 dump, not from a published MusicBrainz statistic.
- **Last.fm coverage and `mbid` lookup reliability.** Requires an API key (an account), which this ticket may not create.
- **Deezer rate limit and album object reference.** Docs are login-gated; the commonly repeated "50 requests per 5 seconds" could not be traced to a Deezer page.
- **Discogs have/want licence class.** Neither the CC0 nor the Restricted list names aggregate counts; the six-hour rule applies to all "Content" regardless.
- **Whether Discogs monthly dumps include have/want.** data.discogs.com describes "Release, Artist, Label, and Master Release data"; not inspected.
- **Fraction of MusicBrainz release groups with a Discogs master or Wikidata URL relationship.** Not published on the statistics page; the Wikidata-side counts above are a lower bound.
